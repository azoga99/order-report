# Интернет-магазин

Бэкенд небольшого интернет-магазина на Java и Spring Boot. Покупатель оформляет заказ из товаров со склада,
выбирает доставку и оплачивает картой, по СБП или наличными. Магазин видит комиссию платёжных систем
и отчёт по продажам за период. Взаимодействие — через REST API, данные хранятся в базе H2.

Проект вырос из консольного отчёта по заказам: способы оплаты и расчёт комиссии остались оттуда.

## Правила магазина

Заказ проходит статусы: **новый → оплачен**, а новый или оплаченный заказ можно **отменить**.
При оформлении товары сразу списываются со склада, при отмене возвращаются. Если какого-то товара не хватает,
заказ не создаётся и ничего не списывается. За отменённый оплаченный заказ возвращается вся сумма.

Доставка:

| Способ    | Стоимость                                   |
|-----------|---------------------------------------------|
| `PICKUP`  | бесплатно                                   |
| `POST`    | 290 руб.                                    |
| `COURIER` | 390 руб., бесплатно при заказе от 5000 руб. |

Комиссия платёжной системы считается от суммы заказа вместе с доставкой и округляется до копеек:

| Способ оплаты              | Ставка |
|----------------------------|--------|
| Карта российского банка    | 1.5 %  |
| Карта зарубежного банка    | 3.5 %  |
| СБП                        | 0.4 %  |
| Наличные                   | 0 %    |

При оплате наличными полученная сумма должна покрывать заказ. От номера карты сохраняются только последние
четыре цифры.

## Архитектура

Проект разложен по слоям Onion-архитектуры, каждый слой — отдельный пакет:

```
src/main/java/org/hse/shop/
  ShopApplication.java           точка входа Spring Boot
  domain/                        доменный слой, без Spring и JPA
    Product, Customer            товар с остатком, покупатель
    Order, OrderItem             заказ с позициями и переходами между статусами
    OrderStatus, DeliveryMethod  статусы заказа и способы доставки
    Payment                      способ оплаты (sealed interface: Card, Sbp, Cash)
    CommissionPolicy             правило расчёта комиссии
    RateCommissionPolicy         комиссия по фиксированным ставкам
    *Repository                  интерфейсы хранилищ
    NotFoundException            объект не найден
    BusinessRuleException        нарушено правило магазина
  application/                   слой приложения: сервисы, по одному на бизнес-задачу
  infrastructure/                всё, что связано с фреймворками
    DomainConfig                 бины для доменных объектов и системных часов
    persistence/                 JPA-сущности, Spring Data и адаптеры хранилищ
    web/                         REST-контроллеры, DTO и обработка ошибок
src/main/resources/
  application.properties         настройки базы H2
  data.sql                       демонстрационные товары и покупатели
src/test/java/org/hse/shop/      тесты, разложены по тем же пакетам
requests.http                    примеры запросов к API
```

Зависимости направлены внутрь:

- `domain` ничего не импортирует из других слоёв, из Spring и из JPA;
- `application` использует только `domain` и аннотации Spring `@Service` и `@Transactional`;
- `infrastructure` использует `application` и `domain`.

Хранилища описаны в домене интерфейсами (`ProductRepository`, `CustomerRepository`, `OrderRepository`),
а реализуют их адаптеры в `infrastructure.persistence`. Адаптер переводит доменный объект в JPA-сущность и обратно,
поэтому аннотаций JPA в домене нет, а сервисы не знают, что данные лежат в H2. Если сменить базу или перейти
с JPA на что-то другое, поменяется только `persistence`.

Доменные объекты неизменяемые (records): операции вроде `order.pay(...)` или `product.take(...)` проверяют правила
и возвращают новый объект, а сервис сохраняет его через хранилище.

## Сервисы

| Сервис                     | Задача                                                                |
|----------------------------|-----------------------------------------------------------------------|
| `ProductCatalogService`    | каталог: добавление товара, просмотр, товары в наличии, смена цены   |
| `StockService`             | склад: поступление, списание под заказ, возврат после отмены         |
| `CustomerService`          | регистрация покупателей, один телефон — один покупатель              |
| `DeliveryCostService`      | стоимость доставки по тарифам                                        |
| `OrderPlacementService`    | оформление заказа: списание товаров, цены из каталога, доставка      |
| `OrderHistoryService`      | заказ по номеру и история заказов покупателя                         |
| `PaymentService`           | оплата заказа и расчёт комиссии                                      |
| `OrderCancellationService` | отмена заказа, возврат товаров на склад и расчёт суммы возврата      |
| `SalesReportService`       | отчёт за период: выручка, комиссии, средний чек, топ-5 товаров       |

Оформление и отмена помечены `@Transactional`: если на середине что-то пошло не так, изменения остатков
откатываются. Время оформления берётся из бина `Clock`, чтобы в тестах его можно было зафиксировать.

## REST API

| Метод  | Путь                                   | Что делает                                     |
|--------|----------------------------------------|------------------------------------------------|
| `GET`  | `/api/products`                        | каталог; `?inStock=true` — только в наличии    |
| `GET`  | `/api/products/{id}`                   | товар                                          |
| `POST` | `/api/products`                        | добавить товар                                 |
| `PUT`  | `/api/products/{id}/price`             | сменить цену                                   |
| `POST` | `/api/products/{id}/supply`            | поступление на склад                           |
| `POST` | `/api/customers`                       | зарегистрировать покупателя                    |
| `GET`  | `/api/customers/{id}`                  | покупатель                                     |
| `GET`  | `/api/customers/{id}/orders`           | история заказов покупателя                     |
| `GET`  | `/api/delivery/cost?method=&itemsTotal=` | стоимость доставки до оформления заказа      |
| `POST` | `/api/orders`                          | оформить заказ                                 |
| `GET`  | `/api/orders/{id}`                     | заказ                                          |
| `POST` | `/api/orders/{id}/payment`             | оплатить                                       |
| `POST` | `/api/orders/{id}/cancel`              | отменить                                       |
| `GET`  | `/api/reports/sales?from=&to=`         | отчёт по продажам, даты вида `2026-09-01`      |

Все запросы с телами и готовый сценарий — в [requests.http](requests.http).

Оформление заказа:

```bash
curl -X POST localhost:8080/api/orders -H "Content-Type: application/json" \
  -d '{"customerId": 2, "delivery": "COURIER", "items": [{"productId": 1, "quantity": 1}, {"productId": 2, "quantity": 2}]}'
```

```json
{"id": 1, "customerId": 2, "status": "NEW",
 "items": [{"productId": 1, "name": "Чайник электрический", "price": 2490.00, "quantity": 1, "amount": 2490.00},
           {"productId": 2, "name": "Кружка керамическая", "price": 350.00, "quantity": 2, "amount": 700.00}],
 "itemsTotal": 3190.00, "delivery": "COURIER", "deliveryCost": 390.00, "total": 3580.00,
 "payment": null, "commission": 0, "createdAt": "2026-09-23T03:03:45"}
```

Оплата картой: в поле `cardNumber` можно передать полный номер, сохранятся только последние четыре цифры.

```bash
curl -X POST localhost:8080/api/orders/1/payment -H "Content-Type: application/json" \
  -d '{"method": "CARD", "cardNumber": "2200 1234 5678 4242", "foreignIssuer": false}'
```

Для СБП передаётся `{"method": "SBP", "phone": "+79161234567"}`, для наличных — `{"method": "CASH", "received": 5000}`.

### Ошибки

Ошибки возвращаются в формате Problem Details (RFC 9457):

| Код   | Когда                                                                     |
|-------|---------------------------------------------------------------------------|
| `400` | некорректные данные: пустое название, телефон не по формату, пустой заказ |
| `404` | товар, покупатель или заказ не найден                                     |
| `409` | нарушено правило: не хватает товара, заказ уже оплачен или отменён        |

```json
{"title": "Conflict", "status": 409, "instance": "/api/orders",
 "detail": "Недостаточно товара «Френч-пресс 600 мл»: на складе 8, нужно 100"}
```

## База данных

Используется встроенная H2 в памяти: при каждом запуске схема создаётся заново по JPA-сущностям
и заполняется из `data.sql` пятью товарами и двумя покупателями. Таблицы: `products`, `customers`,
`orders` и `order_items`. Способ оплаты хранится в колонках заказа, заполненные колонки зависят от `payment_method`.

## Требования

- JDK 21
- Apache Maven 3.9 и новее

## Сборка и запуск

```bash
mvn clean package
java -jar target/shop-1.0-SNAPSHOT.jar
```

или без сборки JAR:

```bash
mvn spring-boot:run
```

Приложение слушает порт 8080.

## Тесты

```bash
mvn test
```

Тесты написаны на JUnit 5, Mockito и AssertJ и разложены по слоям:

- **домен** — валидация и правила товара, покупателя и заказа, ставки комиссии; Spring не поднимается;
- **сервисы** — модульные тесты с заглушками хранилищ и соседних сервисов через Mockito: основные сценарии
  и граничные случаи (пустой заказ, остаток ровно под заказ, наличные ровно на сумму, отчёт за один день);
- **хранилища** — `@DataJpaTest` на H2: сохранение заказа с позициями, каждый способ оплаты, выборка за период;
- **API** — `@SpringBootTest` с `MockMvcTester`: полный путь заказа от оформления до отмены, откат списания
  при нехватке товара, коды ошибок и отчёт по продажам. У теста отчёта своя база и зафиксированные часы,
  чтобы результат не зависел от других тестов и от даты запуска.

## Плагин JaCoCo

В сборку подключён `jacoco-maven-plugin` — он измеряет покрытие кода тестами.
Плагин настроен на три шага:

- `prepare-agent` — подключает агент, который во время прогона тестов собирает данные о выполненных строках;
- `report` — по завершении фазы `test` формирует отчёт в `target/site/jacoco` (HTML, XML, CSV);
- `check` — на фазе `verify` проверяет, что покрытие по строкам не ниже 80 %, и иначе прерывает сборку.

Полный прогон с проверкой покрытия:

```bash
mvn clean verify
```

Отчёт открывается в браузере: `target/site/jacoco/index.html`.
Текущее покрытие — 99 % строк и 92 % ветвлений.
